# Kioku 0.5.1.0 → 0.5.2.0

This edge **entails** `keiro-upgrade` `0.14.0.0 -> 0.15.0.0`, which Seihou has
already run. That edge is the entire substance of this version window.

Keiro 0.15.0.0's breaking change lives in **`keiro-dsl`**: generated and
package-authored record types lost their field selector functions and
owner-prefixed labels in favour of concise repeated labels, and existing
generated projects must explicitly adopt the `idiomatic-v2` generated-Haskell
edition before their next scaffold run will write files. Migrating a project's
`keiro-dsl` code and its recorded scaffold ledgers is that edge's
responsibility. **Do not redo it here, and do not revert a change you find
already made.**

Kioku itself does not depend on `keiro-dsl`. The three Keiro packages Kioku does
consume — `keiro`, `keiro-core`, and `keiro-migrations` — were republished at
0.15.0.0 with no source change at all, so Kioku moved to them by raising bounds
and nothing else. Kioku's own API, runtime behaviour, event codecs, migrations,
and CLI are unchanged across this window.

No other cohort member moves. This release keeps `kiroku-store ^>=0.8.0.0`,
`kiroku-store-migrations ^>=0.4.0.0`, `keiki ^>=0.9.0.0`,
`keiki-codec-json ^>=0.9.0.0`, `shibuya-core ^>=0.9.0.0`,
`shibuya-kiroku-adapter ^>=0.5.1.1`, `baikai ^>=0.6.0.0`, and
`pg-migrate ^>=1.1.0.0` — Keiro 0.15.0.0 requires the same versions of all of
them that 0.14.0.0 did.

## Precondition

Report this edge **not applicable** when the project does not depend on any
Kioku package.

Beyond that, expect *not applicable* to be the honest and common answer even for
projects that do depend on Kioku. There is no Kioku source migration in this
window, no new migration, no changed migration payload, and no ledger fixup. A
project that consumes Kioku and has never used `keiro-dsl` has only Step 1 to
confirm.

Do not manufacture work to justify the edge. Reporting that a project's bounds
already resolve 0.15.0.0 and that nothing else applies is a complete, correct
outcome.

## Step 1 — Confirm the version window

Seihou's normal workflow bumps the dependency first and migrates source up to
it, so the build plan usually already resolves 0.5.2.0 by the time this edge
runs.

Check. If the project still declares 0.5.1-era bounds, raise them now — every
Kioku package it depends on, in lockstep, because their internal bounds are
locked to each other and a partial bump will not solve:

`kioku-api`, `kioku-migrations`, `kioku-core`, `kioku-cli`, `kioku-migrate`.

`keiro`, `keiro-core`, and `keiro-migrations` **do** move to `^>=0.15.0.0`, and
so does the optional `keiro-pgmq` if the project declares it. If the project
names them directly, the entailed Keiro edge has already raised them — verify
rather than re-edit.

Do **not** move `kiroku-store`, `kiroku-store-migrations`, `keiki`,
`keiki-codec-json`, `shibuya-core`, `shibuya-kiroku-adapter`,
`shibuya-pgmq-adapter`, `baikai`, or `pg-migrate`. This release does not move
them, and widening them here would admit a cohort Kioku 0.5.2.0 was never built
against. `shibuya-pgmq-adapter` is the one most likely to be raised by mistake,
because its current version happens to be `0.14.0.0` and looks like a Keiro
version — it is Shibuya's, `keiro-pgmq 0.15.0.0` itself requires `^>=0.14.0.0`
of it, and no newer release exists.

### If the project pins a Hackage index-state

A pin that predates this release's upload makes the solver unable to see it at
all, and no amount of correct source editing will fix that. Advance the pin past
the last upload in this release and run `cabal update` so the local index
carries it. If the project's comment explains which cohort the pin covers,
update that comment too.

If `cabal update` reports the requested index-state is newer than the latest
known one, that is a stale local index, not a bad pin — run `cabal update` again
and retry.

### If the solve fails, read the conflict before editing anything

A project may depend on **another library that itself depends on Kioku**. Such a
library pins its own Kioku bounds, and until *it* publishes a release admitting
0.5.2.0, the solver cannot satisfy both. The conflict names the package and the
bound.

That is a **hard blocker, not a bounds problem in this project**. Do not work
around it with `allow-newer`, a `source-repository-package` override, or bounds
widened beyond what the release supports. Stop, report which package blocks the
solve and which bound of its released version excludes 0.5.2.0, and say the
upgrade needs that library released first.

Report this as a stopped edge, not an inapplicable one: the precondition is met
and the work is real, it is just blocked upstream.

## Step 2 — Confirm the database story is unchanged

There is nothing to do here, and this step exists to let you establish that
cheaply rather than by searching.

Kioku 0.5.2.0 adds no migration, changes no already-released migration payload,
and requires no ledger fixup. The composed plan a project applies through
`kioku-migrate` — or through its own runner composing Kioku's plan after
Kiroku's and Keiro's — is unchanged at **55 migrations: Kiroku 11, Keiro 31, and
Kioku 13**, exactly as under 0.5.0.0 and 0.5.1.0. Keiro 0.15.0.0 republished
`keiro-migrations` with no migration added.

A project that asserts on migration counts or ids therefore needs no edit. If a
count assertion in the project *does* fail after this upgrade, that is not this
edge's change — report it rather than adjusting the number, because the plan
composes three components and something else moved.

A checksum mismatch on any migration is likewise outside this edge. Report it;
do not bypass it.

## Step 3 — Validate

Run the project's normal build and test commands — the ones this repository
actually defines, not a guess. The successful result is a clean build against
`keiro-0.15.0.0`, `keiro-core-0.15.0.0`, and `keiro-migrations-0.15.0.0`, with
every suite passing and no source change of the project's own.

Read back what actually resolved rather than trusting the bound:

```sh
jq -r '."install-plan"[] | select(."pkg-name"|startswith("keiro")) | ."pkg-name" + " " + ."pkg-version"' \
  dist-newstyle/cache/plan.json | sort -u
```

Report any command you could not run, and why, rather than claiming a pass.

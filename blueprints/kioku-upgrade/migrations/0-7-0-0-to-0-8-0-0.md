# Kioku 0.7.0.0 → 0.8.0.0

This edge **entails** `keiro-upgrade` `0.17.0.0 -> 0.18.0.0` and
`0.18.0.0 -> 0.19.0.0`, which Seihou has already run. The second of those
entails `kiroku-upgrade` `0.8.0.2 -> 0.9.0.0`. Keiro's widened ID-domain and DSL
types, the Shibuya 0.10 upgrade, the `pg-migrate` 1.2 family, Keiro's new record
fields, and every Kiroku source and database step, including the cutover for
Kiroku migration `0012`, are those edges' responsibility. Verify their edits; do
not duplicate, paraphrase, or revert them here.

Kioku 0.8.0.0 is a cohort move with no Kioku source or API change. It adds no
Kioku migration and corrects no released payload, so **no Kioku ledger fixup is
required**. The composed migration plan grows from 56 to 57 through Kiroku's
appended `kiroku/0012`.

## Precondition

Report this edge **not applicable** when the project does not depend on any
Kioku package.

A project that depends only on `kioku-api`, and does not use Keiro, Kiroku, or
Kioku's migrations directly, has a lockstep version-and-bounds update only.

## Step 1 — Align the release cohort

Raise every Kioku package the project consumes to `^>=0.8.0.0` in lockstep:

- `kioku-api`
- `kioku-core`
- `kioku-cli`
- `kioku-migrations`
- `kioku-migrate`

Kioku 0.8.0.0 requires Keiro `^>=0.19.0.0`, `kiroku-store ^>=0.9.0.1`,
`kiroku-store-migrations ^>=0.6.0.0`, `shibuya-core ^>=0.10.0.0`,
`shibuya-kiroku-adapter ^>=0.5.1.5`, `keiki ^>=0.9.1.0`, and the `pg-migrate`
family at `^>=1.2.0.0`. If the project declares any of these directly, the
entailed edges have already raised them; verify the result rather than editing
it a second time.

If the project's test suites depend on `kioku-migrations:test-support`, raise
the project's own `ephemeral-pg` bound, if it declares one, to `^>=0.3.1.0`.
That sublibrary now requires it through `keiro-test-support` 0.19.

The Baikai and Shikumi cohorts are unchanged from Kioku 0.7.0.0. Report solver
conflicts instead of adding `allow-newer`, source overrides, or unreviewed pins.

## Step 2 — Move migration counts to 57

This step applies only when the project asserts on Kioku's composed migration
plan: counts, pending ids, positional offsets, or the Kiroku schema comment.

| | Total | Kiroku | Keiro | Kioku |
|---|---|---|---|---|
| 0.7.0.0 | 56 | 11 | 32 | 13 |
| 0.8.0.0 | **57** | 12 | 32 | 13 |

`kiroku/0012` sits between `kiroku/0011` and the first Keiro migration, so any
index or `drop N` offset past the Kiroku component shifts by one. The Kiroku
schema comment now reads
`Managed by pg-migrate component kiroku through 0012`. Recompute such
assertions from the upstream `migrations/manifest` files rather than by adding
one to every literal: a count restricted to Keiro or Kioku does not move.

## Step 3 — Do not apply `0012` to a live database from this edge

A database that holds data and has Kiroku `0011` applied must cross `0012` with
every Kiroku 0.8 writer stopped. That cutover is Part B of the entailed Kiroku
edge. This edge **names it and stops**. Running `kioku-migrate up` against such
a database is the operator's decision on their own backup and maintenance
window. For a database holding data that must not be lost, use the
`cohort-migrate` skill.

Fresh and ephemeral databases, including those the test suites provision, need
no special action.

## Validate

Run the consumer's normal build and tests, including every suite that migrates
and writes to a database. A clean build does not prove a direct `$all` insert
sets `category`; only a write does. If the project owns migration-count
fixtures, prove the composed count is 57.

Do not add migration SQL, apply a ledger fixup, or copy the entailed Keiro or
Kiroku edges' work into this edge.

# Kioku 0.4.1.0 → 0.5.0.0

This edge **entails** `keiro-upgrade` `0.13.0.0 -> 0.14.0.0`, which Seihou has
already run. Keiro's terminal outbox rejection work — the new `PublishOutcome`
and `OutboxStatus` constructors, the new `OutboxRow` fields, and migration
`keiro/0031` — is that edge's responsibility. Do not redo it here, and do not
revert a change you find already made.

No other upstream cohort member moves. This release keeps `kiroku-store
^>=0.8.0.0`, `kiroku-store-migrations ^>=0.4.0.0`, `keiki ^>=0.9.0.0`,
`shibuya-core ^>=0.9.0.0`, `shibuya-kiroku-adapter ^>=0.5.1.1`, `baikai
^>=0.5.0.0`, and `pg-migrate ^>=1.1.0.0`.

Kioku 0.5.0.0 carries three things of its own: the **Rei foreign decoder
retirement**, a **corrected payload for the already-released migration `0011`**
that requires a one-time ledger fixup, and a **new migration `0013`**.

## Precondition

Report this edge **not applicable** when the project does not depend on any
Kioku package.

A project that depends on Kioku but has never written a foreign-format event
still has real work here if it runs `kioku-migrate`, composes Kioku's migration
plan, or asserts on migration counts. Do not report it inapplicable on the
strength of "we never used Rei" — check Step 3 first, because the `0011`
correction reaches every database that has already applied it.

## Step 1 — Confirm the version window

Seihou's normal workflow bumps the dependency first and migrates source up to
it, so the build plan usually already resolves 0.5.0.0 by the time this edge
runs.

Check. If the project still declares 0.4-era bounds, raise them now — every
Kioku package it depends on, in lockstep, because their internal bounds are
locked to each other and a partial bump will not solve:

`kioku-api`, `kioku-migrations`, `kioku-core`, `kioku-cli`, `kioku-migrate`.

Do **not** move `kiroku-store`, `kiroku-store-migrations`, `keiki`,
`shibuya-core`, `shibuya-kiroku-adapter`, `baikai`, or `pg-migrate`: this release
does not move them, and widening them here would admit a cohort Kioku 0.5.0.0
was never built against.

`keiro`, `keiro-core`, and `keiro-migrations` **do** move to `^>=0.14.0.0`, but
if the project declares them directly, the entailed Keiro edge has already
raised them. Verify rather than re-edit.

### If the project pins a Hackage index-state

A pin that predates this release's upload makes the solver unable to see it at
all, and no amount of correct source editing will fix that. Advance the pin past
the last upload in this release and run `cabal update` so the local index
carries it. If the project's comment explains which cohort the pin covers,
update that comment too.

If `cabal update` reports the requested index-state is newer than the latest
known one, that is a stale local index, not a bad pin — run `cabal update` again
and retry.

### If the solve still fails, read the conflict before editing anything

A project may depend on **another library that itself depends on Kioku**. Such a
library pins its own Kioku bounds, and until *it* publishes a release admitting
0.5.0.0, the solver cannot satisfy both. The conflict names the package and the
bound.

That is a **hard blocker, not a bounds problem in this project**. Do not work
around it with `allow-newer`, a `source-repository-package` override, or bounds
widened beyond what the release supports. Stop, report which package blocks the
solve and which bound of its released version excludes 0.5.0.0, and say the
upgrade needs that library released first.

Report this as a stopped edge, not an inapplicable one: the precondition is met
and the work is real, it is just blocked upstream.

## Step 2 — The Rei foreign decoder retirement

This is the change that will not announce itself. **The types did not change.**

`Kioku.Memory.EventStream.parseMemoryEvent` and
`Kioku.Session.EventStream.parseSessionEvent` keep the signature
`Value -> Either Text Event`. What changed is the language they accept: they no
longer decode Rei's retired `agent_memory_*`, `agent_session_*`, or
`interactive_session_recorded` tags. Those values now return `Left`.

A project that fed such payloads through an ordinary replay will compile
cleanly, pass a type check, and fail at runtime — or worse, dead-letter events
it used to absorb. The compiler cannot help you here.

### Precondition for this step

Report this step not applicable only after checking. Grep the project for:

- the literal tags `agent_memory_`, `agent_session_`, `interactive_session_recorded`;
- call sites of `parseMemoryEvent` and `parseSessionEvent`;
- any fixture, seed file, or test payload whose event `type` field carries one
  of those tags;
- any Rei-era import or migration tool the project still ships.

A project whose only event history was written by Kioku itself is genuinely
unaffected by this step. Say so and move on.

### What is still supported

Do not over-correct. Kioku's **native** backwards compatibility is unchanged and
must not be worked around:

- pre-partition Kioku payloads still decode and still land in the
  `kioku_legacy` memory space;
- `SessionResumed` payloads written before the `force` field existed still
  decode with their established default.

If you find code defending against those, leave it alone. This edge removes
foreign application vocabulary only.

### What a project that *is* affected must do

Per ADR-11 (`consumers-own-one-time-foreign-event-migration-codecs`), the
translation is now this project's to own. There are three legitimate outcomes,
and the choice is the project's, not yours:

1. **Migrate the history** — copy the foreign events into native Kioku streams
   with a finite, one-time migration tool. It may use Kioku's domain
   constructors and native encoders; the foreign tag dispatch and identifier
   normalization live in this project.
2. **Keep a consumer-owned decoder** — retain the translation as a
   compatibility component this project maintains, invoked explicitly rather
   than through the ordinary parser.
3. **Explicitly abandon support** — decide the foreign history will not be
   read again, after preserving whatever inventory and recovery boundary that
   retention decision requires.

Report which outcome the project needs and what it would take. **Do not pick one
and implement it silently** — option 3 is a product decision about data
retention, and option 1 is a migration against real history. Both belong to the
project's owners.

### What not to do

- Do not match on the `Left` error text to detect a foreign payload and route
  around it. The message is not a stable interface.
- Do not re-encode foreign payloads to look native so the parser accepts them.
  That launders unvalidated data into the native language and loses the marker
  that says this history was foreign.
- Do not vendor Kioku's deleted decoder back in unchanged and call it done.
  If the project takes option 2, the decoder is now this project's supported
  code — it needs the project's own tests.

## Step 3 — The `0011` payload correction and its ledger fixup

**Read this even if Step 2 was not applicable.** It reaches every database that
has already applied Kioku migration `0011`.

Kioku 0.4.0.0 and 0.4.1.0 shipped a payload for
`0011-kioku-memory-space-partition.sql` whose plain
`SET search_path TO kiroku, pg_catalog` survived transaction commit on the
connection pg-migrate reuses for a composed plan. A later host component on that
connection could therefore fail to resolve its own unqualified tables. The
corrected `0011` resets the session value before committing.

Correcting the payload changes its checksum:

| | SHA-256 |
|---|---|
| withdrawn (0.4.0.0, 0.4.1.0) | `eee9cd252b32b563c50f8457596347fff1b2e4d3ea4dafe5b45043e991624192` |
| corrected (0.5.0.0) | `6c83d3f01f784d0d9395953d5bb1763b8eea6cd9439073df42f79775a85197a9` |

pg-migrate verifies the exact SHA-256 of every applied payload, so a database
that already applied the withdrawn payload reports `MigrationChecksumMismatch`
until its stored checksum is re-baselined.

### Establish which case this project is in — from read-only evidence

- **A database where `0011` is still pending** applies the corrected payload
  normally. No fixup, no special action.
- **Fresh and ephemeral databases** — anything the project's own tooling
  recreates from scratch, including CI — need nothing.
- **A long-lived database that already applied `0011` under 0.4.0.0 or 0.4.1.0**
  needs the one-time re-baseline, once, before its next `up` or `verify`.

### What the operator must run

`kioku-migrations` ships the script in its source distribution at
`ledger-fixups/2026-08-19-rebaseline-0011-checksum.sql`. It is available to
Hackage consumers, not only from a git checkout.

Its properties, so you can describe it accurately:

- It updates exactly one row — the applied `kioku/0011` row carrying the exact
  withdrawn checksum — and nothing else.
- It is idempotent. A second run, a pending migration, an already-corrected row,
  or any other checksum changes zero rows and raises a notice.
- It assumes pg-migrate's default ledger schema, `pgmigrate`. A project that
  configured a different schema through `LedgerConfig` changes the schema name
  in the one `to_regclass` call and nowhere else. The script raises a clear
  exception rather than guessing.
- **No schema migration follows it.** The withdrawn and corrected payloads have
  identical durable schema and data effects; the only withdrawn effect was a
  connection-local `search_path` that ceased to exist when the old runner
  connection closed.

### Your boundary here

**Do not run this against a database holding real data.** Report that the
operator must take a verified backup and run it once per affected database,
before the next `up` or `verify`.

If the project has a disposable development database, running the fixup and then
`kioku-migrate verify` against it is a legitimate way to prove the sequence — say
so in your report, and keep it clearly separate from the production runbook.

This is a narrow, evidenced correction to one known checksum. It is **not**
permission to bypass any other checksum mismatch. If the project hits a mismatch
on a different migration, stop and report it.

## Step 4 — Migration `0013` and the composed plan's shape

`kioku-migrations` 0.5.0.0 adds `0013-partition-aware-fts-index.sql`. It is
**purely additive** — it changes no existing migration's payload, and needs no
fixup of its own.

When `btree_gin` is installed or can be installed, it replaces the content-only
full-text GIN with an active-only GIN over
`(memory_space_id, namespace, content_tsv)`, so one space's recall cost stops
growing with matching content in unrelated spaces. If extension installation is
unavailable, the migration succeeds and retains the old index as a
correctness-preserving fallback. A project that cannot install extensions is
therefore not blocked — it simply does not get the improvement.

### Migration counts changed

The composed plan is now **55** migrations: Kiroku 11, Keiro 31, Kioku 13. It
was 53 at 0.4.x (Kiroku 11, Keiro 30, Kioku 12) — Keiro's `0031` comes from the
entailed edge, and Kioku's `0013` from this one.

If the project asserts a **count** of pending or applied migrations, or an
expected list of migration ids, update those fixtures. This is a common source
of a green build with a red test suite.

### Operational note for a large `kioku.memories`

Read this before running it against production. Building a GIN index over an
active-row predicate on a large table takes time and holds locks. Do not rewrite
the migration to avoid this — its checksum is recorded and editing it
desynchronizes every database that applies it. Size the window instead, and
schedule accordingly.

## Step 5 — Smaller surfaces, only if the project uses them

Each of these is a "check whether it applies" item, not a required change.

- **`kioku-api` gained `underMemoryContext` and `inLegacyMemorySpaceOnly`** —
  generic `Applicative` helpers that apply an existing context's permission,
  space, and actor decision in a fixed order. They are additive. They **consume**
  a context; they do not mint or widen one. A project with its own hand-rolled
  copy of that gate ordering may now share Kioku's, but nothing forces it.

- **`kioku recall --strategy` now uses the canonical parser** from
  `Kioku.Api.Recall`. Accepted values and the default are unchanged, so a script
  calling the CLI is unaffected. A project that reimplemented the strategy
  spellings can now use `recallStrategyText`, `parseRecallStrategy`, and
  `allRecallStrategies` instead.

- **Distillation now preflights permissions** before reading evidence, calling a
  model, mutating a derived row, or writing a mirror. L1 requires
  `MemoryDistill`, `MemoryRecord`, and `MemoryForget`; L2/L3 timer fires require
  `MemoryDistill` and reject a context for the wrong space. A project whose
  distillation ran under an under-scoped context was previously doing work it
  was not authorized for and will now see it refused **earlier and louder**.
  That is the fix working. Grant the right permissions rather than widening the
  space.

- **Memory lineage targets are validated within their space.** Every
  `supersedes`, `supersededBy`, and merge-winner target must exist in the source
  memory's space before the first transition. Missing and cross-space targets
  both return `MemoryNotFound` without appending an event. A test that
  previously relied on a lineage write to a nonexistent or cross-space target
  succeeding will now fail — correctly.

- **Embedding backfills are scoped by space**, and the missing-or-stale
  content-hash predicate now runs in the SQL rather than only in Haskell.
  Behavior is the same; the row transfer is much smaller. A project asserting on
  query shape or row counts in an embedding test may need updating.

## Proving it

Run the project's own build and test commands — the ones this repository
actually defines, not assumed ones. At minimum:

- the build must succeed against the raised bounds;
- any suite covering event decoding, memory lineage, distillation, embeddings,
  or migration plans must pass;
- if Step 2 applied, the project must have a stated plan for its foreign
  history — a passing build is not evidence that the history is safe, because
  the retirement is invisible to the compiler.

If the project has a disposable development database, `kioku-migrate verify`
followed by `up` against it proves the composed plan applies end to end at 55
migrations. Do not run either against a database holding real data as part of
this edge; Step 3 is the guidance for that case.

Report which commands you ran, which you could not, and why.

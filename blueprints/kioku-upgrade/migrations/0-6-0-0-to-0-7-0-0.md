# Kioku 0.6.0.0 → 0.7.0.0

This edge **entails** `keiro-upgrade` `0.16.0.0 -> 0.17.0.0`, which Seihou has
already run. Keiro's work-queue ordering, guarded dead-letter operations,
deterministic outbox identity, record additions, DSL changes, and optional PGMQ
cohort are that edge's responsibility. Verify its edits; do not duplicate or
revert them here.

Kioku 0.7.0.0 adopts Keiro 0.17 comprehensively. Its own public change is the
replacement of legacy read-model freshness controls with explicit
`ReadModelBlueprint` values and validated projection-catalog registration.
The composed migration plan remains at 56. No released migration payload
changed and **no ledger fixup is required**.

## Precondition

Report this edge **not applicable** when the project does not depend on any
Kioku package.

A project that depends only on `kioku-api`, and does not use Keiro directly,
has a lockstep version-and-bounds update only. A project that neither calls
Keiro's read-model API directly nor owns Kioku runtime assembly can finish
after the dependency solve and its normal tests pass.

## Step 1 — Align the release cohort

Raise every Kioku package the project consumes to `^>=0.7.0.0` in lockstep:

- `kioku-api`
- `kioku-core`
- `kioku-cli`
- `kioku-migrations`
- `kioku-migrate`

Kioku 0.7.0.0 requires the Keiro 0.17 lockstep family. If the project declares
Keiro packages directly, the entailed edge has already raised them; verify the
result rather than editing it a second time.

If the project declares the optional PGMQ family directly, verify the entailed
edge moved `pgmq-config`, `pgmq-core`, `pgmq-effectful`, `pgmq-hasql`, and
test-only `pgmq-migration` to `>=0.6 && <0.7`, plus
`shibuya-pgmq-adapter` to `^>=0.16.0.0`. Do not add these dependencies to a
project that does not use them.

The Kiroku, Keiki, Shibuya core, Baikai, and Shikumi cohorts are otherwise
unchanged from Kioku 0.6.0.0. Report solver conflicts instead of adding
`allow-newer`, source overrides, or unreviewed pins.

## Step 2 — Replace direct use of legacy Keiro freshness APIs

This step applies only when the project calls Keiro's read-model APIs directly.
Search source and tests for:

```text
ConsistencyMode
StrongScope
Eventual
EntireLog
runQueryWith
defaultConsistency
strongScope
subscriptionName
```

Treat matches as review candidates, not automatic substitutions. Replace
legacy consistency-mode configuration with a truthful `ReadModelBlueprint`:

- use `NoQueryCursor` for read models that cannot provide durable query
  cursors;
- use `DurableQueryCursor` only when the read model actually persists and
  reports that cursor;
- construct blueprints with the public Keiro 0.17 builders instead of filling
  deprecated compatibility records;
- express each query's wait requirement as `QueryFreshness`; and
- call `runQueryWithFreshness` when selecting freshness explicitly.

Do not silence deprecation warnings. Compile the consumer with
`-Werror=deprecations` after the edits so a test-only or rarely built component
cannot retain the compatibility API unnoticed.

## Step 3 — Preserve validated catalog registration

Kioku's standard `withNoopAppEnv` assembly now validates one projection catalog
and registers it with Keiro before serving queries. Projects that use Kioku's
standard environment need no extra call.

A host that owns custom runtime assembly must preserve the same boundary:
construct one catalog from the read-model blueprints it actually installs,
validate it before startup succeeds, and register that catalog with Keiro.
Do not maintain a separate hand-written readiness list alongside the catalog;
derive readiness and reconciliation targets from the validated catalog.

## Step 4 — Keep the migration plan at 56

Kioku 0.7.0.0 adds no migration. Keiro 0.17.0.0 also adds no migration relative
to the 0.16 cohort, so the composed plan remains:

| | Total | Kiroku | Keiro | Kioku |
|---|---|---|---|---|
| 0.6.0.0 | 56 | 11 | 32 | 13 |
| 0.7.0.0 | **56** | 11 | 32 | 13 |

Keep fixtures, deployment checks, and runbooks at 56. There is **no ledger
fixup** for this release. A checksum mismatch is outside this edge: report it
and investigate rather than changing the ledger or bypassing verification.

## Validate

Run the consumer's normal build and tests, plus a build that treats deprecations
as errors. For a Cabal project, the minimum additional gate is:

```sh
cabal build all --ghc-options=-Werror=deprecations
```

If the project owns runtime assembly, add or retain a startup test proving an
invalid or duplicate projection catalog is refused before queries are served.
If it owns migration-count fixtures, prove the composed count is still 56.

Do not add migration SQL, apply a ledger fixup, or copy the entailed Keiro
edge's PGMQ, outbox, DLQ, metrics, or DSL work into this edge.

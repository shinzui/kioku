# Kioku 0.12.0.2 → 0.13.0.0

## Precondition

The consumer moves any Kioku 0.12 release to 0.13.0.0. Keep its five Kioku
packages aligned. The entailed edges from mori://shinzui/keiro cover Keiro
0.22 → 0.23 → 0.24, including the Store 0.13 edge from mori://shinzui/kiroku.
Use Mori to inspect dependency sources and the consumer's actual build plan.

## Cohort and source

Require Keiro 0.24.0.0, Kiroku Store 0.13.0.1, Store migrations 0.7.3.0 and
the Kiroku Shibuya adapter 0.7.0.1. Replace any consumer project constraint
`kiroku-store-migrations ==0.7.2.0` with `==0.7.3.0` to match the qualified
plan. Do not add `allow-newer` to conceal incompatible bounds.

Rebuild embedded hosts, the CLI and workers together. The upstream edges own
exhaustive Store/error/observer matches, projection status wrappers and embedded
operational hooks. Inspect these only where used. Kioku's native event encodings,
query catalog, exact-category subscriptions and AI configuration are unchanged.
The Shikumi 0.5 and Trace 0.3.1 bounds inherited from Kioku 0.12.0.2 support
Baikai 0.10; remove the older Shikumi-to-Baikai exceptions if still present.

## Database and validation

The plan grows from 63 to 64 entries: 17 Kiroku, 32 Keiro and 15 Kioku.
A complete 0.12 database has only `kiroku/0017` pending. This installs one
immutable store identity and an empty compaction ledger; it does not compact
events. Historical SQL and recorded checksums do not change. No new ledger
fixup or Kioku query-catalog adoption is required.

Classify persistent data read-only. Rehearse on a disposable restored clone,
preserve events, stream positions, projections, subscription bindings and
checkpoints, and prove a repeat run is a no-op. Follow this repository's
`docs/user/upgrading-to-keiro-0-24.md` operator runbook. Apply persistent changes
through the host's composed runner only as an operator action. Do not drop
persistent databases, fabricate ledger entries or enable compaction privileges.

Build with exhaustive-pattern checks, run the consumer's tests and verify its
migration plan. Report resolved versions, source changes, rehearsal evidence
and pending operator work. A package installation or source-migration receipt
does not apply database migrations.

# Kioku 0.5.2.0 → 0.6.0.0

This edge **entails** `keiro-upgrade` `0.15.0.0 -> 0.16.0.0`, which Seihou has
already run. Keiro's timer resume claims and leases — the upstream API and its
migration `keiro/0032` — are that edge's responsibility. Do not redo that work
here, and do not revert a change you find already made.

Kioku 0.6.0.0 carries three things of its own:

1. **AI execution becomes host-owned and explicit.** Every AI-touching entry
   point now dispatches through an `AIRuntime` the host constructs from a
   configuration file. Most of this is a loud compile error. **One part is
   not** — see Step 2.
2. **A new embedding-model compatibility refusal**, which can turn a previously
   working recall or backfill into a runtime refusal without any source change
   in the project.
3. **The composed migration plan grows to 56**, entirely from the entailed
   Keiro edge's `keiro/0032`. No Kioku migration payload changed and **no
   ledger fixup is required**.

The Baikai and Shikumi cohorts also move — `baikai`, `baikai-claude`, and the
newly required `baikai-openai` to `^>=0.7.0.0`, `baikai-effectful` to
`^>=0.4.0.1`, `shikumi` to `^>=0.4.0.0`, and `shikumi-trace` to `^>=0.3.0.0`.
Neither library publishes an upgrade blueprint, so what a Kioku consumer needs
from those moves is covered inline here.

## Precondition

Report this edge **not applicable** when the project does not depend on any
Kioku package.

Beyond that, expect the edge to be **applicable and substantial** for most
projects that do depend on `kioku-core`. Unlike the 0.5.1.0 → 0.5.2.0 window,
this one is not bounds-only: it changes exported signatures, removes an
environment-variable configuration path, and adds a runtime refusal.

A project that depends only on `kioku-api` has a version bump and nothing else —
that package's source and API are unchanged. Say so and move on.

## Step 1 — Confirm the version window

Seihou's normal workflow bumps the dependency first and migrates source up to
it, so the build plan usually already resolves 0.6.0.0 by the time this edge
runs.

Check. If the project still declares 0.5-era bounds, raise them now — every
Kioku package it depends on, in lockstep, because their internal bounds are
locked to each other and a partial bump will not solve:

`kioku-api`, `kioku-migrations`, `kioku-core`, `kioku-cli`, `kioku-migrate`.

`keiro`, `keiro-core`, and `keiro-migrations` **do** move to `^>=0.16.0.0`, and
so does the optional `keiro-pgmq` if the project declares it. If the project
names them directly, the entailed Keiro edge has already raised them — verify
rather than re-edit.

The AI cohort **does** move. If the project declares any of these directly,
raise them: `baikai`, `baikai-claude`, `baikai-openai` (`^>=0.7.0.0`),
`baikai-effectful` (`^>=0.4.0.1`), `shikumi` (`^>=0.4.0.0`), `shikumi-trace`
(`^>=0.3.0.0`). `baikai-openai` is **newly required** by `kioku-core` — a
project that pins its transitive dependencies explicitly must add it.

Do **not** move `kiroku-store`, `kiroku-store-migrations`, `keiki`,
`keiki-codec-json`, `shibuya-core`, `shibuya-kiroku-adapter`,
`shibuya-pgmq-adapter`, or `pg-migrate`. This release does not move them, and
widening them here would admit a cohort Kioku 0.6.0.0 was never built against.

If Kioku 0.5.1.0 required an `http-client-tls` selection or a Baikai TLS
override in the project's `cabal.project`, check whether it is still needed.
Kioku dropped its own obsolete Baikai TLS overrides in this release. Remove a
workaround only if the project's own solve succeeds without it — do not remove
one that is load-bearing for a different dependency.

### If the project pins a Hackage index-state

A pin that predates this release's upload makes the solver unable to see it at
all, and no amount of correct source editing will fix that. Advance the pin past
the last upload in this release and run `cabal update` so the local index
carries it. If the project's comment explains which cohort the pin covers,
update that comment too.

If `cabal update` reports the requested index-state is newer than the latest
known one, that is a stale local index, not a bad pin — run `cabal update` again
and retry.

### If the solve fails, read the conflict before editing anything

A project may depend on **another library that itself depends on Kioku**. Such a
library pins its own Kioku bounds, and until *it* publishes a release admitting
0.6.0.0, the solver cannot satisfy both. The conflict names the package and the
bound.

That is a **hard blocker, not a bounds problem in this project**. Do not work
around it with `allow-newer`, a `source-repository-package` override, or bounds
widened beyond what the release supports. Stop, report which package blocks the
solve and which bound of its released version excludes 0.6.0.0, and say the
upgrade needs that library released first.

Report this as a stopped edge, not an inapplicable one: the precondition is met
and the work is real, it is just blocked upstream.

## Step 2 — Host-owned AI execution

This is the substance of the release. Read the whole step before editing,
because its two halves fail in opposite ways: the first half will not compile
until you fix it, and the second half compiles perfectly while doing nothing.

### 2a. The signature changes — the compiler will find these

Kioku no longer activates a provider, selects a model, or reads a credential on
its own. A host constructs an `AIRuntime` and passes it in.

| Before (0.5.2.0) | After (0.6.0.0) |
|---|---|
| `newDistillRuntime :: IO DistillRuntime` | removed; build from an `AIRuntime` |
| `DistillRuntime (..)` — constructor and fields exported | `DistillRuntime` — abstract |
| `recall :: EmbeddingModel -> …` | `recall :: AIRuntime -> …` |
| `Kioku.Distill.L1.recallCandidates :: EmbeddingModel -> …` | `recallCandidates :: AIRuntime -> …` |
| `resolveEmbeddingConfig :: IO EmbeddingConfig` | `resolveEmbeddingConfig :: AIRuntime -> AIFeature -> Either AIExecutionError EmbeddingModel` |
| `mkEmbeddingWorkerEnv :: EmbeddingModel -> Int -> EmbeddingWorkerEnv` | `mkEmbeddingWorkerEnv :: AIRuntime -> Either AIExecutionError EmbeddingWorkerEnv` |
| `runEmbeddingWorkerHost … EmbeddingModel -> Int -> …` | `runEmbeddingWorkerHost … AIRuntime -> …` |
| `embeddingWorkerProcessor … EmbeddingModel -> Int -> …` | `embeddingWorkerProcessor … EmbeddingWorkerEnv -> …` |

**A caller that already owns an `EmbeddingModel` and wants exactly the old
behaviour has a rename, not a rewrite.** The previous shapes are still exported,
unchanged:

- `Kioku.Recall.recallWithEmbeddingAdapter` is the old `recall`.
- `Kioku.Distill.L1.recallCandidatesWithEmbeddingAdapter` is the old
  `recallCandidates`.

These adapters exist for hosts that already resolve models themselves. Prefer
them over reconstructing a runtime **only** when the project genuinely owns its
own model selection. If the project was relying on Kioku to pick the model, the
adapter is the wrong answer — it will make the code compile while leaving the
project with no model at all.

Error constructors also consolidated. Pattern matches on these will fail to
compile, which is the point:

- `L1ExtractionFailed` and `L1ConsolidationFailed` → `L1ExecutionFailed !AIExecutionError`
- L2's scene-generation failure → `L2ExecutionFailed !AIExecutionError`
- L3's persona-generation failure → `L3ExecutionFailed !AIExecutionError`
- `RecallError` gains `RecallAIUnavailable !AIExecutionError`

The replacements carry a structured `AIExecutionError` where the old ones
carried a rendered `Text`. Do not `show` it back into the old string shape to
avoid touching a log format — the structure is the improvement.

`DistillRuntime` is abstract now, so a test that built one by record syntax must
move to the explicit test seam: `testDistillRuntime`, then `withTestRunners` to
supply controlled runners and `withDistillWorkspace` to pin the workspace root.
`EmbeddingConfig`'s derived `Show` is replaced by a redacting instance; a test
asserting on its rendered output must change, and a log that printed it was
leaking a credential.

### 2b. The environment variables that stopped working — the compiler cannot help you

**This is the part of the release that fails silently.**

Kioku 0.5.2.0 configured embedding from the environment. Kioku 0.6.0.0 does not
read any of these:

- `KIOKU_EMBEDDING_BASE_URL`
- `KIOKU_EMBEDDING_MODEL`
- `KIOKU_EMBEDDING_DIMENSIONS`
- `KIOKU_EMBEDDING_API_KEY`
- `OPENAI_API_KEY` (as a Kioku-level fallback)

A deployment that set them and nothing else will **build cleanly, start
cleanly, and have AI disabled**. Semantic recall degrades to keyword search with
a warning on stderr; the embedding worker refuses; distillation refuses. Nothing
crashes and no type changed.

The rule is deliberate: **credentials no longer enable AI, configuration does.**
An absent configuration means disabled, not "guess from the environment".

#### What to grep for

Search the project — and its deployment surface, not only its Haskell source:

- the five variable names above, in `.hs`, `.nix`, `.yaml`, `.yml`, `.env`,
  `Dockerfile`, Helm charts, CI definitions, systemd units, and shell wrappers;
- any `docker-compose`, Kubernetes manifest, or secrets template that injects
  them;
- documentation and runbooks that tell an operator to set them.

`OPENAI_API_KEY` needs care: it is a widely used variable and the project may
set it for something other than Kioku. Finding it is not proof of breakage —
finding it *as the only thing configuring Kioku's embeddings* is.

#### Do not treat a passing build as evidence

A green `cabal build` and a green test suite say nothing about this step. If the
project's suites stub the AI runtime — and most do — they will pass in exactly
the configuration that is broken in production.

The check that actually means something is behavioural: with the project's real
configuration loaded, confirm that a feature which should be enabled reports
itself enabled, rather than confirming that the process started.

#### The replacement

Configuration is an explicit JSON file, selected by `--ai-config FILE` on the
CLI, by the `KIOKU_AI_CONFIG` environment variable, or by an embedding host
calling `Kioku.AI.File.loadAIRuntime`. It is versioned (`"version": 1`) and
names, per feature, the execution mode, provider, model, endpoint, and where the
credential comes from.

Kioku ships worked examples at `docs/examples/ai-api.json` and
`docs/examples/ai-interactive.json` in its source distribution. The API-mode
shape is roughly:

```json
{
  "version": 1,
  "permissions": ["api"],
  "distillation": {
    "mode": "api",
    "api": "anthropic-messages",
    "provider": "anthropic",
    "model": "claude-haiku-4-5",
    "baseUrl": "https://api.anthropic.com",
    "options": {"apiKeyEnv": "ANTHROPIC_API_KEY", "maxTokens": 4096}
  },
  "features": {},
  "embeddings": {
    "memory-embedding": {"mode": "api", "model": "text-embedding-3-small", "baseUrl": "https://api.openai.com", "dimensions": 1536, "apiKeyEnv": "OPENAI_API_KEY"},
    "query-embedding":  {"mode": "api", "model": "text-embedding-3-small", "baseUrl": "https://api.openai.com", "dimensions": 1536, "apiKeyEnv": "OPENAI_API_KEY"},
    "candidate-embedding": {"mode": "api", "model": "text-embedding-3-small", "baseUrl": "https://api.openai.com", "dimensions": 1536, "apiKeyEnv": "OPENAI_API_KEY"}
  }
}
```

Note that the credential still lives in an environment variable — `apiKeyEnv`
names which one. **Do not write a literal key into this file**, and do not
commit a file that contains one.

The seven features are configured independently: `extraction`, `consolidation`,
`scene`, `persona`, `memory-embedding`, `query-embedding`, and
`candidate-embedding`. A project that only wants semantic recall configures the
embedding features and leaves distillation disabled; that is a supported
configuration, not a partial one.

**Reconstructing the project's intended configuration is the project's
decision, not yours.** Report which features the project was previously using
and what a file expressing that would contain. Do not invent a provider, model,
or endpoint the project never chose, and do not enable a feature that costs
money on the strength of a variable you found in a CI file.

### 2c. Interactive mode and background workers

The release adds an interactive execution mode, in which a feature runs through
a locally launched agent session rather than an API call. A background worker
**never** receives interactive session ownership — that is enforced, not
conventional.

The consequence for an operator: a timer whose feature is configured
`interactive` cannot fire in the background. Instead of failing permanently or
retrying forever, the worker now dead-letters it with a `deferred` outcome
naming the memory space, and the work is resumed later in an authorized
foreground session:

```sh
kioku worker deferred list
kioku worker deferred resume TIMER_ID --ai-config FILE
```

Resume rechecks permissions and execution availability, renews the lease, fences
finalization, and re-parks failed work for bounded retry — it preserves the
original parked work rather than synthesizing new work.

If the project runs Kioku's background workers and configures any distillation
feature as `interactive`, its runbook needs the resume step. If it configures
everything as `api`, this does not apply.

## Step 3 — The composed migration plan grows to 56

Kioku 0.6.0.0 adds **no migration of its own** and changes **no already-released
migration payload**. There is **no ledger fixup in this window**.

The plan still grows, because the entailed Keiro edge appends `keiro/0032` for
timer resume claims and leases:

| | Total | Kiroku | Keiro | Kioku |
|---|---|---|---|---|
| 0.5.2.0 | 55 | 11 | 31 | 13 |
| 0.6.0.0 | **56** | 11 | **32** | 13 |

If the project asserts a **count** of applied or pending migrations, or an
expected list of migration ids, update those fixtures to 56. This is the most
common way this window produces a green build with a red suite.

Apply the pending migration before using deferred timer discovery or resume —
`keiro/0032` is what the lease and claim columns live in.

A checksum mismatch on any migration is outside this edge, because this release
corrects none. Report it; do not bypass it.

## Step 4 — The embedding-model compatibility refusal

This can change runtime behaviour with no source change in the project, so check
it even when Step 2 was straightforward.

Kioku now records which embedding model a memory space's vectors were written
with, and **refuses** to mix models rather than comparing incomparable vectors.
When a space's stored model differs from the configured one:

- semantic and hybrid recall return
  `RecallAIUnavailable (AIExecutionRefused …)` rather than wrong results;
- L1 candidate search refuses with `L1ExecutionFailed`;
- the embedding worker dead-letters the message as an invalid payload, and a
  backfill over a mismatched space refuses.

This is the guard working. A project that hits it has a real data condition: its
stored vectors were produced by a different model than the one it now
configures.

**The remedy is to re-embed the affected memory space, and that is the
project's decision to schedule** — it re-runs an embedding model over stored
content and costs real money and time proportional to the space's size. Report
which spaces are affected and what re-embedding them would take.

Do **not** work around it by configuring whichever model happens to match the
stored vectors unless that is genuinely the model the project wants, and do
**not** disable the check. A mismatch that is silently tolerated produces recall
results that look plausible and are meaningless.

The most likely way to trigger this accidentally is Step 2b: a project whose
`KIOKU_EMBEDDING_MODEL` set a non-default model, and whose new configuration
file omits it and falls back to a different one. Check the old variable's value
against the new file before concluding the data is at fault.

## Step 5 — Validate

Run the project's normal build and test commands — the ones this repository
actually defines, not a guess. At minimum:

- the build must succeed against the raised bounds, with no `allow-newer`;
- any suite covering recall, distillation, embeddings, timers, or migration
  plans must pass;
- migration count fixtures must reflect 56.

Read back what actually resolved rather than trusting the bound:

```sh
jq -r '."install-plan"[] | select(."pkg-name"|test("^(kioku|keiro|baikai|shikumi)")) | ."pkg-name" + " " + ."pkg-version"' \
  dist-newstyle/cache/plan.json | sort -u
```

If the project has a disposable development database, `kioku-migrate up`
followed by `verify` against it proves the composed plan applies end to end at
56 migrations. Do not run either against a database holding real data as part of
this edge.

**A passing build is not a complete result for this edge.** Say explicitly, in
your report, what you established about Step 2b — which of the five retired
environment variables the project set, where, and what configuration replaces
them — because that is the one part of this window a green build actively hides.

Report which commands you ran, which you could not, and why.
